## 一、项目概况

### 1.1 基本信息
- **游戏类型**：2D 俯视角·多层堆叠·滑块归位解谜
- **目标平台**：微信小游戏（纯前端）
- **变现模式**：纯 IAA（应用内广告）— 第一期未接入
- **技术栈**：TypeScript + Canvas 原生渲染 + Vite 构建
- **代码仓库**：`f:\work\小游戏\挪挪`

### 1.2 技术选型理由
| 项目 | 选择 | 理由 |
|---|---|---|
| 引擎 | 原生 Canvas + TypeScript | 不依赖 Cocos，零基础也能看懂；微信小游戏原生支持 |
| 语言 | TypeScript | 有类型提示，IDE 智能补全，降低出错率 |
| 构建工具 | Vite | 极快的热更新，浏览器实时预览 |
| 微信适配 | 后续适配层 | 一套代码，浏览器调试 + 微信打包 |

### 1.3 开发命令
- `npm run dev` → 浏览器开发预览（自动刷新，端口 3000）
- `npm run editor` → 启动关卡编辑器（自动打开 `/editor.html`）
- `npm run build` → 浏览器版本打包
- `npm run build:wx` → 微信小游戏打包（待配置）

**一键启动脚本**（双击即可，无需敲命令）：
- `启动.bat` → 启动服务器并自动打开游戏 + 编辑器两个标签页
- `启动游戏.bat` → 启动服务器并打开游戏本体
- `启动编辑器.bat` → 启动服务器并打开关卡编辑器
- `停止服务器.bat` → 停止后台运行的服务器

> ⚠️ 不能直接双击 `index.html` / `editor.html` 打开。项目使用 ES Module + TypeScript，必须通过本地服务器访问（`http://localhost:3000/`），否则浏览器会拦截模块加载。

> 编辑器入口页面：项目根目录 `editor.html`（与游戏 `index.html` 完全隔离）。

### 3.4 编辑器架构（v0.6.0 新增）
编辑器是一个**独立的开发期工具页面**，与游戏本体共享同一个 Vite 工程，但代码、入口、画布全部隔离：

- **入口隔离**：游戏走 `index.html`，编辑器走 `editor.html`，互不污染。微信小游戏打包时编辑器不会被包含。
- **数据隔离**：编辑器只读取游戏的 `types/`、`config/GameConfig.ts`、`config/LevelConfig.ts`（只读），不依赖 `Board` / `SceneGame` 等运行时类。
- **渲染独立**：`EditorRenderer` 从 `LevelConfig` 直接画棋盘，复用 `GameConfig` 颜色和 `itemAssets` 图标，做到"所见即所得"。
- **试玩桥接**：试玩时复用 `GameApp` / `InputManager` 单例，通过 `SceneGame` 新增的可选参数注入自定义 config。

### 3.2 核心数据结构
- **CellData**：棋盘格子数据，含 `stack`（堆叠）、`portalId`/`portalUses`（传送门）、`freezeCounter`（水洼倒计时）、`placedCount`【v0.6.2】（目标格已归位物品数，支持无限容量）、`onewayDir`【v0.7.0】（单向门方向）、`buttonId`/`buttonPressed`/`barrierId`/`barrierKind`/`barrierActive`【v0.8.0】（按钮与活动墙/桥运行时态）
- **LevelConfig**：关卡 JSON 配置，含棋盘/障碍/传送门/水洼/单向门/`buttons`/`activeBarriers`【v0.8.0】/物品/目标/刷新次数/`winCondition`【v0.6.2】（通关模式：placeAll 全归位 / clearItem 消除指定物品 X 个）
- **MoveResult**：移动结果，含是否传送、实际落点坐标
- **GameStateData**：全局运行时状态，含关卡进度/移动次数/刷新次数/移动历史
- **MoveRecord**：移动记录，用于撤销功能

### 3.3 设计原则
1. **高性能**：对象池复用、Canvas 原生渲染无引擎开销
2. **高扩展性**：事件总线解耦、系统可插拔、配置与代码分离
3. **高可维护性**：单一职责、TypeScript 类型约束、全中文注释

## 八、关键决策记录

### 7.1 为什么用原生 Canvas 而不是 Cocos？
- 零基础友好，代码可读性强
- 无引擎运行时开销，性能更好
- 微信小游戏原生支持 Canvas API
- 包体更小（无引擎代码）

### 7.2 为什么 CellData 要有 stack 字段？
- 最初 Board 的 cell 只存一个物品，导致堆叠时后写入覆盖先写入
- 引入 stack 后，Board 成为堆叠数据的唯一数据源
- moveItem 自动处理堆叠暴露，不需要外部手动恢复 cell
- 渲染直接遍历 stack 画堆叠效果

### 7.3 为什么死局检测只查 layer=1？
- 简单版检测只检查"当前能否一步到达目标格"
- 被压住的下层物品（layer>1）当前不可移动，检查它们会误报
- 完整死局检测需要多步搜索（NP 困难），后续版本再实现

### 7.4 为什么用事件总线而不是直接调用？
- 场景切换时需要通知多个模块（HUD/音效/结算）
- 事件总线解耦，新功能只需订阅事件，不改动老代码

### 7.5 为什么传送门要用 MoveResult 而不是 boolean？
- 传送后物品的实际落点和玩家拖放位置不同
- SceneGame 需要知道实际落点来更新物品运行时数据和归位判断
- MoveResult 包含 teleported 标志，方便日志和后续动画处理

### 7.6 为什么传送门有使用次数限制？
- 增加策略深度：玩家需要规划何时使用传送门
- 避免无限传送导致关卡过于简单
- 次数显示在传送门上（Nx），信息透明，玩家可据此规划

### 7.7 为什么编辑器要独立成 editor.html 而不是嵌进游戏？（v0.6.0）
- 编辑器是开发期工具，不应进入微信小游戏发布包
- 独立入口让游戏运行时和编辑器互不污染，降低耦合
- 共享 Vite 工程可以复用类型定义和配置，不用维护两套工程

### 7.8 为什么 EditorRenderer 不直接复用 BoardRenderer？（v0.6.0）
- BoardRenderer 依赖运行时 Board 类（含动态 stack、物品状态），编辑器场景下没有 Board 实例
- 编辑器只有静态 LevelConfig，"从 config 直接画"比"先构造 Board 再画"更简单可控
- 颜色和图标通过独立 `itemAssets.ts` 与游戏保持同步，避免反向依赖

### 7.9 为什么试玩要给 SceneGame 加参数而不是写一个独立预览场景？（v0.6.0）
- 复用真实 SceneGame 能保证"试玩 = 玩家实际体验"，机制一致性 100%
- 加可选参数 `config?` + `isTrial` 完全向后兼容，现有 `new SceneGame(level)` 调用零改动
- 试玩模式跳过 `unlockLevel` 和结算跳转，避免污染玩家存档；通关/返回通过 `onTrialEnd` 回调通知编辑器

### 7.10 为什么美术资源要建统一加载层 + 全程回退？（v0.6.1）
- 游戏本体和编辑器都要用同一套美术，抽 `GameAssets.ts` 避免两边各加载一份、各写一份映射
- 美术资源是逐步产出的（目前只 6/8 种物品 + 部分地形），所有渲染路径必须能回退到 emoji/色块，否则缺图就白屏
- `preloadAssets()` 在启动时一次性加载，渲染时直接取缓存，避免运行时异步画图导致首帧空缺
- 物品按 `ITEM_ART_ID` 解耦：以后换图案只改图片文件，新增物品类型只改映射表一行，不动渲染代码

### 7.11 为什么堆叠用"阶梯式向下偏移"而不是"右下偏移"？（v0.6.1）
- UI 设计图要求下层从顶层**下方**露出一条边缘（约 8px），模拟实物堆叠的视觉
- 旧的右下偏移会让下层同时向右和向下露出，视觉重心偏移，不像"叠在一起"
- 阶梯式向下递增（每层 +8px）配合绘制顺序（先下层后上层），下层顶部被覆盖、底部露出，最贴近设计图
- 透明度从每层 0.3 降到 0.15：主要靠偏移区分层次，透明度太低反而看不清下层是什么

### 7.12 为什么按钮触发态以"回合开始时快照"为准？（v0.8.0）
- "压住即触发"若在拖拽路径预演中途实时翻转墙/桥态，会出现"边拖边变路"的歧义，玩家难以预判落点
- 改为路径预演统一用本回合开始时的按钮态快照：玩家看到的高亮就是本次可落点，行为可预期
- 移动落地后再 `recalcButtons()` 结算翻转，影响下一回合——"压按钮→墙消失→另一物品下一回合借机通过"的逻辑在跨回合层面成立
- 这是回合制解谜的标准做法：单回合内状态稳定，回合边界结算变化

### 7.13 为什么按钮与活动墙/桥用"共享 id 扁平数组"而非嵌套 pair 对象？（v0.8.0）
- 沿用传送门已验证的配对模式（`portals` 扁平数组 + 共享 `portalId`），降低学习与维护成本
- 扁平数组天然支持后续扩展"一按钮控多墙/桥"：本期校验强制每个 id 恰好 1 按钮 + 1 墙/桥，扩展时只需放宽校验让同 id 的多个墙/桥同步响应，数据结构零改动
- 嵌套 pair 对象在多对多场景下反而笨重，且与现有传送门/单向门等"扁平配置数组"风格不一致

### v0.7.0（2026-07-19）- 单向门机制 + 编辑器支持

**机制语义**（GDD v1.1 新增机制 3）：
- 单向门格子带方向箭头（上/下/左/右），物品沿箭头方向移动时可**进入、穿过、停留**在该格。
- 反向（及垂直方向）移动时，单向门视为障碍物：不可进入、不可穿过。
- 物品停在门格上后，下一次移动离开门格**不受方向限制**（方向判定只发生在"进入时"）。
- 撤销移动不受单向门限制（撤销绕过 PathCalculator 直接 moveItem）。

**背景**：原20关仅用了部分机制（堆叠/传送门/水洼），单向门/按钮墙桥/clearItem均未实装到关卡。扩展到100关并按"起承转合"节奏编排。同时，玩家反馈"复合关卡缺少策略性、缺少紧迫感"，决定重新引入步数限制（v0.4.0曾取消），并用A*求解器自动计算每关最优步数以设定合理的maxSteps。

**16章节结构**（玩家不可见）：

#### 二、A*求解器（`scripts/solver.mjs`）

**目的**：求出每关最优解步数，用于设定maxSteps = ceil(最优解 × 容错系数)。

**实现**：
- 状态空间搜索：状态=棋盘快照（物品位置+机关状态+水洼倒计时+传送门次数+placedCount），状态哈希去重
- A*启发函数：Σ(未归位物品到最近匹配目标的曼哈顿距离)，含传送门距离，admissible
- 二叉堆优先队列（MinHeap），节点上限20万，时间上限10秒/关
- 超时降级：贪心+随机重启10次取最短作为估算值

**容错系数**（按章节递减制造"越来越紧"体验）：
| 章节 | 系数 | 体验 |
|---|---|---|
| Ch1-3 | ×1.6 | 宽松，教学期不卡步 |
| Ch4-7 | ×1.45 | 引入期略紧 |
| Ch8-10 | ×1.35 | 组合期 |
| Ch11-13 | ×1.25 | 稀缺峰最紧，频繁"差一两步" |
| Ch14-16 | ×1.3 | 极限期略松回 |

**求解结果**：100关中 精确解41关 / 估算59关 / 无解23关。

### v0.8.2（2026-08-23）- 编辑器体验增强

**背景**：编辑器功能齐全但操作反馈弱、UI 偏小：试玩无法看到实际步数（配置 maxSteps 靠猜）、步数上限无输入口、覆盖/新增本关需手动下载再改名覆盖、手机端布局错乱、FAQ 说明缺失、字体小导致"眼睛痛"。

#### 一、试玩结算显示移动步数
- `SceneGame.ts`：`onTrialEnd` 签名改为 `(reason: 'complete' | 'home', moves?: number)`；4 处调用点（onLevelComplete 用 `data.moves`，onLevelFailed/giveUpLevel/回家用 `gameState.moveCount`）均携带步数
- `main.ts`：`endTrial(reason, moves)` 在通关/放弃时弹 `trial-result` 弹窗显示"实际移动步数：X 步"；主动点"返回编辑器"不弹

#### 二、步数上限必填输入（0=无限制）
- `editor.html`：新增 `#max-steps-input`（min=0 max=999，附"必填项：填 0 表示无步数限制"提示）
- `EditorState.ts`：新增 `setMaxSteps(v)`，0/负数→存 `undefined`（无限制）
- `main.ts`：change 事件绑定 + `updatePropertyInputs` 回显 `cfg.maxSteps ?? 0`
- `EditorValidator.ts`：maxSteps 必须是非负整数
- 关键约束：`maxSteps: 0` 在 GameState 中 `stepsLeft >= 0` 会开局即失败，导出时 0/undefined 必须省略字段

#### 三、覆盖/新增本关直接写回 `src/config/LevelConfig.ts`
- `vite.config.ts`：新增 `levelConfigSaver` 插件，`configureServer` 中间件 `/api/save-level-config`，仅允许写 `src/config/*.ts`，POST {file, content}
- `EditorStorage.ts`：新增 `saveLevelConfigFile()`（fetch POST）；`generateLevelConfigFile` 导出时 maxSteps>0 才写字段
- `main.ts`：`btnOverwrite`/`btnAppend` 从"下载文件"改为直接 `await saveLevelConfigFile(text)`，成功提示"已写入! 刷新后生效"
- 注意：中间件仅 dev server 生效，生产构建不加载；写回仅限编辑器 dev 环境
